## Rule-file conflicts

1. **`nextjs.md` Route Handler example vs. written `api-fetch.md`:** the example calls `apiFetch` directly in a Route Handler, while the written API-fetch rule says Route Handlers call functions exported from `*.api.ts`. Follow the written `api-fetch.md` rule.
2. **`nextjs.md` ProductList example and `mutations.md` query example vs. server-first/API-fetch rules:** examples use client `useQuery` and import an API module into a client hook. This conflicts with the written server-first rule and the prohibition on client imports of `*.api.ts`. Keep client fetching only for data genuinely driven by client state/interactivity or real-time needs.
3. **`mutations.md` direct-fetch examples vs. written `api-fetch.md`:** mutation/query examples call raw `fetch` for backend requests, while the written API-fetch rule requires the shared helper. Follow `api-fetch.md`.
4. **`mutations.md` form example vs. written `forms.md`:** examples use `form.register()`, while the written form rule requires the `Controller`/`Field` pattern. Follow the written form rule.
5. **`forms.md` examples vs. its written schema-location convention:** some examples place schemas in `features/auth/schemas`, while the written convention specifies `lib/schemas`. Follow the written convention.
6. **`auth.md` proxy redirect example vs. locale-aware routing:** the example redirects to a locale-less auth URL, conflicting with locale-preserving auth redirects and i18n routing. Preserve the active locale.
7. **`auth.md` raw-fetch example vs. written `api-fetch.md`:** the auth example uses direct `fetch` for a backend request, conflicting with the shared API helper rule. Use `apiFetch` from the appropriate server API function.
