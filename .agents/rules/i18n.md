# Internationalization — next-intl v4

## Supported Locales

```typescript
// i18n/routing.ts
import { defineRouting } from "next-intl/routing";

export const routing = defineRouting({
  locales: ["en", "ar"],
  defaultLocale: "en",
});

export type Locale = (typeof routing.locales)[number];
```

---

## Translation Namespaces

Nest message keys one level. The top key is the namespace passed to `useTranslations` or `getTranslations`. Keys inside that object stay flat.

```json
// ✅ src/i18n/messages/en.json — one level of nesting
{
  "Login": {
    "title": "Login",
    "username": "Username",
    "password": "Password"
  }
}
```

```tsx
const t = useTranslations("Login");

t("username");
```

```json
// ❌ Avoid — a second level of nesting
{
  "Login": {
    "username": { "label": "Username" }
  }
}
```

## Navigation Imports

Always import locale-aware navigation utilities (`Link`, `redirect`, `usePathname`, `useRouter`) from the project's `i18n/navigation.ts` — never from `next/navigation`. This ensures locale handling works correctly. Utilities with no locale-aware version (`useSearchParams`, `notFound`, `useParams`) still come from `next/navigation`.

```typescript
// i18n/navigation.ts
import { createNavigation } from "next-intl/navigation";

import { routing } from "./routing";

export const { Link, redirect, usePathname, useRouter, getPathname } =
  createNavigation(routing);
```

```typescript
// ✅ Good — locale-aware navigation
import { useRouter, usePathname, Link } from "@/i18n/navigation";

// ✅ Good — next-intl hooks
import { useTranslations, useLocale } from "next-intl";

// ✅ Good — no locale-specific version exists
import { useSearchParams, notFound } from "next/navigation";

// ❌ Bad — bypasses locale handling
import { useRouter, usePathname, Link } from "next/navigation";
```

The `redirect` from `i18n/navigation.ts` needs the locale passed explicitly:

```typescript
import { redirect } from "@/i18n/navigation";

redirect({ href: "/auth/login", locale });
```

## Using Translations in Server Components

```typescript
// src/app/[locale]/products/page.tsx
import { getTranslations } from "next-intl/server";

export default async function ProductsPage() {
  const t = await getTranslations("Header");

  return <h1>{t("products")}</h1>;
}
```

## Using Translations in Client Components

```typescript
"use client";

import { useTranslations } from "next-intl";

export function AddToCartButton() {
  // Translation
  const t = useTranslations("Header");

  return <button>{t("cart")}</button>;
}
```

## RTL Support

Set `dir` on the root `<html>` element based on locale:

```typescript
// src/app/[locale]/layout.tsx
import { NextIntlClientProvider } from "next-intl";

import { routing } from "@/i18n/routing";

const rtlLocales = ["ar"];

export default async function LocaleLayout({
  children,
  params,
}: {
  children: React.ReactNode;
  params: Promise<{ locale: string }>;
}) {
  const { locale } = await params;
  const dir = rtlLocales.includes(locale) ? "rtl" : "ltr";

  return (
    <html lang={locale} dir={dir}>
      <body>
        <NextIntlClientProvider>{children}</NextIntlClientProvider>
      </body>
    </html>
  );
}
```

## RTL-aware Tailwind Classes

Use logical CSS properties (`ms-*`, `me-*`, `ps-*`, `pe-*`, `text-start`, `text-end`) in shared components instead of directional properties. This ensures layout works correctly in both LTR and RTL.

```typescript
// ✅ Good — works in Arabic (RTL) and English (LTR)
<div className="ms-4 pe-6 text-start">
<ul className="ps-4">

// ❌ Bad — breaks in RTL
<div className="ml-4 pr-6 text-left">
<ul className="pl-4">
```

## Number & Date Formatting

Always use locale-aware formatting with `Intl`:

```typescript
// ✅ Good
const formatted = new Intl.NumberFormat(locale, {
  style: "currency",
  currency: "EGP",
}).format(price);

const date = new Intl.DateTimeFormat(locale, {
  dateStyle: "long",
}).format(new Date(createdAt));
```

## next-intl Proxy

In Next.js 16, `middleware.ts` was renamed to `proxy.ts`. The next-intl code itself is unchanged. `middleware.ts` still works but is deprecated and logs a warning.

```typescript
// proxy.ts (project root, or src/ if you use it)
import createMiddleware from "next-intl/middleware";

import { routing } from "./i18n/routing";

export default createMiddleware(routing);

export const config = {
  matcher: ["/((?!api|_next|.*\\..*).*)"],
};
```

- This app default-exports `proxy` from `src/proxy.ts` and combines auth with this middleware. A named export must be `proxy`, not `middleware`.
- The proxy runs on the Node.js runtime, not Edge.
- Only one `proxy.ts` is allowed per project. Combine auth and i18n logic inside it.
- To rename automatically: `npx @next/codemod@canary middleware-to-proxy .`

## Rules Summary

- ✅ Nest message keys one level (`Login.username`). Avoid a second level of nesting
- ✅ Import `useRouter`, `usePathname`, `Link` from `@/i18n/navigation` — not `next/navigation`
- ✅ Use logical Tailwind classes (`ms-*`, `ps-*`, `text-start`) in shared components
- ✅ Set `dir` on `<html>` from locale
- ✅ Pass `locale` to all `Intl` number/date formatters
- ❌ Never use `text-left` / `text-right` in shared/reusable components
